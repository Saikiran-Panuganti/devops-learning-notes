# Data Transfer Object (DTO)

## Definition

**DTO** stands for **Data Transfer Object**. It is a design pattern used to
carry data between different layers of an application or between services.

Simply put:

> **DTO = A container that carries data from one place to another without
> carrying business logic.**

Think of a DTO like a parcel: you pack only the information the receiver needs,
then send it from one system or application layer to another.

## DTO and Data Formats

A DTO is not a serialization format. It describes the data an application
intends to transfer; that data can be serialized into formats such as JSON,
XML, or YAML.

| Term | Meaning | Purpose |
|---|---|---|
| YAML | YAML Ain't Markup Language | Human-readable configuration and data serialization |
| JSON | JavaScript Object Notation | Data exchange and serialization |
| XML | Extensible Markup Language | Structured data representation and exchange |
| DTO | Data Transfer Object | Carries selected data between application components |

For example, the user DTO above is represented in JSON. The DTO is the
selected data structure; JSON is the format used to serialize it.

## Example

Suppose an application stores a user's name, email address, password hash,
internal database ID, and other information. A public API should not expose all
of those fields. It can use a DTO to send only the information the client
needs:

```json
{
  "name": "Alex",
  "email": "alex@example.com"
}
```

The DTO defines the data being transferred. It does not decide business rules
such as whether the user is allowed to update their email address.

## Why Use a DTO?

- Transfer only the data the receiver needs.
- Avoid exposing internal or sensitive fields.
- Keep the data exchanged between application components explicit.
- Separate data-transfer structure from business logic and internal data
  models.

## How Are DTOs Useful in DevOps?

DTOs are application design patterns, not DevOps tools like Docker,
Kubernetes, Terraform, or Ansible. They are still relevant in DevOps because
applications deployed and operated by DevOps teams often use APIs and
microservices to exchange data.

| DevOps area or tool | Common format or structure | How DTOs or the format are useful |
|---|---|---|
| Microservices | DTO serialized as JSON or another format | Defines the fields one service sends to another |
| REST APIs | JSON request and response bodies | DTOs shape the API data; JSON is the serialization format |
| CI/CD pipelines | JSON test data; YAML pipeline definitions | Pipelines can test API request/response contracts; pipeline YAML defines build and deployment steps |
| Kubernetes | YAML manifests; API objects commonly represented as JSON | Manifests describe desired cluster resources; they are configuration, not application DTOs |
| Docker | Dockerfile (plain-text instructions); JSON in some image metadata | Dockerfiles describe how to build an image; they are not DTOs |
| Terraform | HCL configuration; JSON is also supported | Describes desired infrastructure resources; it is configuration, not a DTO |
| Ansible | YAML playbooks and inventory data | Describes automation tasks and hosts; it is configuration, not a DTO |
| Monitoring and events | JSON payloads or text-based metrics | DTOs can define structured event or API data; metrics formats represent measurements |
| API integration | JSON, XML, or other agreed formats | DTOs help standardize which fields are exchanged between applications |

For example, an order service may send a JSON payload containing an order ID,
customer ID, and items to a payment service. The DTO defines the agreed data
fields; JSON encodes those fields for transmission. A Kubernetes YAML manifest
may deploy both services, but that manifest configures infrastructure and is
not itself a DTO.
