# Configuration Management

Configuration management (CM) is the process of automating server setup,
software installation, configuration updates, and maintaining consistency
across multiple servers.

For example, if you need to install Nginx on 100 servers, configuring each one
manually takes time and can lead to mistakes or differences between servers.
With a configuration management tool, you describe the desired configuration
once on a CM server or control node, then use the tool to apply it to the
servers. This makes the work faster, repeatable, and more consistent.

# Configuration Management Approaches 
The two common configuration management approaches are:

![Diagram comparing pull-based and push-based configuration management](https://github.com/Saikiran-Panuganti/Images/blob/main/02.Ansible/Pull_Push_Config.png)


1. **Pull-based configuration management**
2. **Push-based configuration management**

## 1. Pull-Based Configuration Management

### Definition

In a pull-based model, an agent runs on each managed server. The agent
periodically contacts the CM server to check for configuration changes. If
changes are available, the agent downloads and applies them.

### Workflow

```text
Managed server                         CM server
     |                                      |
     |--- Agent checks for updates -------->|
     |                                      |
     |<------ Configuration changes -------|
     |                                      |
     +--- Agent applies the changes         |

        (For example, every 30 minutes)
```

### Real-Time Example

Suppose a company has 100 Linux servers and needs Nginx installed on all of
them. The administrator defines the required configuration on the CM server.
Each server's agent checks the CM server every 30 minutes. When an agent next
checks in, it retrieves the configuration and installs Nginx. As a result,
servers receive the change at different times, depending on when they check in.

### Tools

- **Chef** and **Puppet** commonly use an agent-based pull model.
- **SaltStack** commonly uses agents, but also supports other operating
  patterns, including agentless SSH.

### Disadvantages

- Changes may not be applied until the next polling interval.
- Agents continue to communicate with the CM server, including when there are
  no changes.
- Agent processes use CPU, memory, and network resources.
- Agents must be installed, upgraded, monitored, and troubleshot on managed
  servers.


## 2. Push-Based Configuration Management

### Definition

In a push-based model, the CM control node initiates a connection to managed
servers and runs configuration tasks when requested. An agent is not required
on the managed servers. For Linux hosts, Ansible typically connects over SSH.

### Workflow

```text
Administrator runs a playbook
             |
             v
       Ansible control node
         /      |      \
       SSH     SSH     SSH
        /        |        \
    Node-1     Node-2     Node-3
```

### Real-Time Example

Suppose a company needs Nginx installed on 100 Linux servers. The
administrator writes an Ansible playbook describing the installation and runs
it from the control node. Ansible connects to the managed servers over SSH and
installs Nginx. The rollout starts when the playbook is run; completion time
depends on connectivity, server availability, and task execution.

### Tool

- **Ansible** is a popular push-based configuration management tool. For Linux
  hosts, it typically uses SSH and does not require an Ansible agent on each
  managed server.

### Advantages

- No Ansible agent installation or maintenance is required on Linux managed
  servers.
- The administrator controls when a playbook runs, rather than waiting for an
  agent polling interval.
- It avoids the ongoing polling performed by an agent-based pull model.
- It uses standard SSH for Linux hosts.
- It can be straightforward to introduce in small and medium-sized
  environments.

### Interview answer

> In push-based configuration management, a control node initiates connections
> to managed servers and runs configuration tasks when requested. Ansible
> commonly uses SSH for Linux hosts and does not require an agent on those
> hosts. This avoids agent maintenance and polling delays, although the control
> node must be able to reach the managed servers and have the required access.

## Quick Comparison

| Feature | Pull-Based | Push-Based |
|---|---|---|
| Communication | Managed-server agent checks for changes | Control node initiates configuration tasks |
| Agent on managed servers | Commonly required | Not required for Ansible's SSH-based Linux management |
| Examples | Chef, Puppet, SaltStack (commonly agent-based) | Ansible |
| Update timing | Agent polling interval can delay changes | Starts when the operator runs the playbook |
| Resource usage | Agents and periodic check-ins use resources | No Ansible agent or periodic agent polling on managed hosts |
| Maintenance | Managed-server agents need maintenance | Less agent maintenance; control-node access and credentials still need management |
| Typical Linux connection | Agent-to-server communication | SSH |
